# AI ExecutionKit v2.2 — Runtime, Discovery & Evidence

**Status:** CANONICAL historical scope for the 34 additions introduced by v2.2.0.  
**Architecture at v2.2.0:** the existing six capabilities remained authoritative; that release added executable subsystems/adapters rather than another OS. **Current v2.2.4 adds State OS separately as cross-cutting system #7 without changing this historical 34-item scope or the six capability levels.**  
**Parallel sessions:** intentionally out of scope and unsupported as an ExecutionKit operating model. Runtime execution is sequential by default. Bounded host-native delegation may be used for one lifecycle action at a time, but the kit does not fan work out into parallel sessions.

## Non-negotiable invariants

- Canonical TODO/native task authority remains the sole mutable task-state owner.
- Agent OS owns routing/orchestration context, not task state.
- Runtime/checkpoint/discovery/evidence artifacts are derived and live under `.executionkit/` by default; they MUST NOT become a backlog.
- New adapters MUST be deterministic about detection, command, raw input, normalized output and evidence identity.
- Optional external tools MUST fail as `NOT_AVAILABLE`/`NOT_CONFIGURED` when absent; they MUST NOT fabricate a PASS.
- Acceptance evidence binds to a candidate/commit/environment and an explicit producer.
- Discovery establishes an implementation denominator; approved planned scope still comes from project authority and contracts.
- No parallel-session scheduler, resource governor or session fan-out exists in v2.2.

State OS in v2.2.4 extends the derived continuity model with `.executionkit/state/`, live rehydration and Amnesia proof. It is documented normatively in `STANDARD.md` and `docs/architecture/state-os.md`; it is intentionally **not** retroactively inserted into this 34-item historical list.
