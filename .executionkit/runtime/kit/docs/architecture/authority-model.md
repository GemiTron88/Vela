# Authority Model — current 3.x

**Status:** CANONICAL architecture derived from `STANDARD.md` + `STANDARD_V3.md`.

## Separate authorities

- **Intent:** approved specifications/contracts.
- **Implemented reality:** current repository/schema/config/runtime/environment evidence.
- **Remaining executable work:** canonical `TODO.md` / configured native source only.
- **Lifecycle semantics:** Execution OS/config/native task adapter or projection.
- **AI routing/orchestration:** Agent OS manifest/resolver/runtime adapter; registered resources must also be deterministically routable.
- **Content truth:** Content OS owns content inventory, provenance/rights, localization, editorial lifecycle and content-quality criteria/evidence.
- **Organic-search truth:** SEO OS owns applicability, search intent/entity/page-family architecture, crawl/index/canonical policy, Search Surface Contracts, specialized search modes and S0–S5 search gates.
- **Independent challenge:** Audit OS owns evidence-first review/challenge and finding/risk disposition without taking over the authority it audits.
- **Verification evidence:** Test OS owns test strategy, executed checks, adequacy/freshness and reproducible evidence; generic browser/Lighthouse/performance/schema commands do not become SEO authority.
- **Release/deployment:** Launch OS owns identifiable candidate/environment, release authorization, deployment, rollback and production verification while invoking applicable candidate-bound SEO gates.
- **Execution continuity:** State OS is cross-cutting system #8; it reconstructs current context from live truth plus derived checkpoints and never owns task state.

The current control plane therefore has exactly **seven capability authorities** — Execution, Agent, Content, SEO, Audit, Test and Launch — plus **State OS as system #8**. Fleet Agent, MCP, Antigravity and Elmasna3 are integrations/subsystems, not additional operating systems.

`.agents` is routing/orchestration authority, never mutable task-state authority. `.executionkit/state`, SEO contracts/evidence, detailed phase/task contracts, quality reports, audits, discovery inventories and handoffs may carry criteria/evidence/context but never a second mutable queue. Archives contain terminal history only.

## Search/quality boundary

SEO applicability exists only where public organic-search intent/surfaces justify it. `NONE` / evidence-backed `NOT_APPLICABLE` is valid for private/authenticated/API/native-only products. Route/database existence does not imply index eligibility and programmatic indexability is fail-closed until distinct intent, visible value and declared coverage are proven.

Content OS owns the underlying content and provenance. SEO OS owns search architecture/index policy. Test OS executes and evaluates evidence against declared criteria. Audit OS independently challenges denominator/implementation/evidence. Launch OS authorizes release/deployment. No validator, Lighthouse score, schema syntax or repository file guarantees indexing, rankings, rich results, traffic or search-engine behavior.

## Contradictions

Stale documentation cannot override current implementation reality. Conversely, existing code does not prove it matches intended requirements. Reconcile contradictions before accepting/closing affected work.

A current canonical document that teaches READY-only scheduling, legacy `VERIFIED` as preferred fresh closure, fewer than seven capability authorities, State OS as a capability level/system other than #8, SEO hidden under Content/performance, or registered-but-unroutable Agent integration is authority drift and must be corrected/demoted. Intentionally historical version documents remain historical rather than being rewritten into current semantics.

## Root binding

Root `AGENTS.md` binds repository-level instructions, canonical TODO/native authority, current standard overlay and `.agents` routing. Execution/Agent/State/SEO validators enforce their applicable structural boundaries; file presence alone is not acceptance.

Current 3.x execution uses `DEPENDENCY_SAFE_PARALLEL` for explicitly safe implementation/resume work. One orchestrator owns canonical claims/integration; parallel workers cannot create another task queue or mutable ownership lane, and any ambiguity falls back to sequential execution. `/boost` changes only the safe concurrency ceiling.

## Evidence boundary

Repository/file validation cannot prove a user's unseen local worktree, an installed IDE/MCP runtime, a physical runner inventory, an exact-candidate executable suite, live production behavior or external search-engine outcomes. Such claims require direct current evidence from the applicable environment/candidate.

`IMPLEMENTED` remains non-terminal. A static integration, committed test or code already present on `main` does not manufacture `ACCEPTED`, PASS, certification, release readiness or publication/promotion evidence.
