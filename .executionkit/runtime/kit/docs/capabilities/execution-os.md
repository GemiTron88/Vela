# Execution OS Capability — current 3.x

**Status:** CANONICAL capability guidance.  
**Mandatory:** Yes.  
**Purpose:** Govern canonical work state, dependency readiness, lifecycle completion, evidence-backed acceptance and safe wave/phase/project closure.

## Execution is the task-state control plane

Execution is the only capability allowed to own mutable executable work state. Agent, Content, SEO, Audit, Test and Launch cooperate with Execution but MUST NOT maintain competing task queues or status ledgers. State OS is cross-cutting continuity/reconstruction and likewise never owns mutable task state.

- Agent OS resolves who/context/workflow handles the current lifecycle action.
- Content, SEO, Audit, Test and Launch may discover requirements/findings/gates in their own authority domains.
- State OS makes the current execution position reconstructable across interruptions without selecting work independently.
- Any independent executable work discovered by another capability maps to the canonical TODO/native task authority before implementation.
- Wave/phase audit gates are canonical tasks when they require execution/state; prose phase tables do not replace them.
- SEO contracts, audit reports, test evidence, launch checklists and State snapshots are inputs/evidence, never shadow backlogs.

## Responsibilities

Execution covers:

- project preflight and pre-execution reconciliation;
- canonical TODO/native task authority and immutable task IDs;
- semantic task lifecycle and native-state projection;
- Definition of Ready and acceptance/closure rules;
- dependency graph and readiness;
- active phase/workstream/wave sequencing;
- lifecycle-aware next-action resolution;
- implementation/correction/resume protocol;
- discovered work/change control;
- evidence capture and task acceptance;
- archive eligibility and terminal history;
- Git/commit/push protocol where project policy requires it;
- wave/phase/project closure;
- failure recovery;
- generated progress reporting;
- execution integrity validation.

Execution does **not** decide organic-search policy. SEO OS owns search applicability, page-family intent/value, technical/index/canonical policy and S0–S5 SEO gate semantics; Execution only owns canonical tasks generated by those decisions/findings and their dependency placement.

## Lite footprint

Suitable for small projects.

May consist of:

- `AGENTS.md`;
- `TODO.md` or an explicitly configured native authority;
- compact Execution OS guidance;
- Agent OS at LITE;
- validator configuration.

It still needs explicit lifecycle, dependencies, Definition of Ready, acceptance evidence and launch boundary when applicable. If work is too small for meaningful waves, use a phase/project boundary audit rather than inventing fake ceremony. SEO may be `NONE`/`NOT_APPLICABLE` only when the actual public-surface/product-intent decision supports that result.

## Standard footprint

Recommended for most production projects.

Includes:

- repository-wide AGENTS authority binding;
- structured canonical TODO/native projection;
- per-phase/task detail files when TODO would become large;
- explicit phase gates and bounded wave gates where useful;
- evidence references;
- Agent OS routing and reviewer separation;
- execution validation and manual self-hosted CI gates;
- generated progress/closure reporting.

## Full footprint

Use for very large or high-risk projects.

Adds where useful:

- workstream/wave contracts within phases;
- richer dependency/risk metadata;
- stronger requirement/task/test/audit traceability;
- recovery/runbook references;
- branch/release-candidate discipline;
- independent wave/phase/release evidence;
- stricter validator rules;
- explicit bounded context envelopes;
- bounded host-native delegation controls for the one selected lifecycle action.

Full MUST NOT mean repeating all product specifications inside Execution OS, creating a second audit/SEO backlog or creating parallel ExecutionKit task ownership.

## Lifecycle-aware next-action resolution

Fresh semantic work is not closed merely because implementation exists. The default closure scheduler prioritizes required boundary/candidate completion before accumulating new implementation:

1. dependency-ready canonical tasks declaring `Action: audit` -> `audit` through independent Audit reviewer routing;
2. `IMPLEMENTED` / `REVIEW_REQUIRED` -> `review` or `revalidate` with an independent reviewer where required;
3. `CORRECTION_REQUIRED` -> `correct`;
4. `IN_PROGRESS` -> `resume` (unless its declared valid special action routes it differently);
5. `BLOCKED` -> `inspect_blocker` only when the canonical task declares a bounded AI-actionable unblock action;
6. dependency-ready ordinary `READY` -> `implement`.

`Action: audit` MUST declare `Audit Boundary: ad-hoc|wave|phase|release`. Unsupported declared actions and invalid/missing audit boundaries fail closed; they do not fall back to implementation.

`PLANNED` is not executable until Definition of Ready promotes it to `READY`.

External/non-actionable blockers remain visible to closure but MUST NOT starve unrelated dependency-ready work. A scheduler that only scans unchecked/READY implementation while audit/candidate/correction work exists is non-conformant.

## Dependencies and closure

Hard dependencies are satisfied only by configured semantic accepted/released states. New projects SHOULD use `ACCEPTED`; `VERIFIED` exists only as an explicitly configured migration compatibility alias.

Normal required work reaches independent `ACCEPTED` before execution closure. `RELEASED` is stronger. `CANCELLED` is terminal only with rationale and does not satisfy dependencies unless the project explicitly and safely overrides that rule.

Phase/project closure is false while any required non-terminal canonical work remains, including candidate/review, correction, blocked or required audit-gate work.

When an Audit or SEO gate discovers executable remediation, map it to canonical TODO/native tasks, keep the owning gate non-terminal where applicable, add the required dependencies and re-run the gate only after remediation is accepted. This lets the normal dependency scheduler route correction/implementation without giving another OS a private queue.

## Bounded wave protocol

A wave is a dependency-aware batch used to control context, integration risk and resource usage. It is not a parallel status system.

For material production work:

```text
wave tasks converge/are accepted
-> focused A1 wave audit of changes + integration seams
-> applicable SEO wave checks for affected public page families
-> map material findings to canonical TODO tasks
-> remediate/reproduce findings
-> targeted integration/regression checks
-> accept wave-audit gate
-> unlock dependent next wave
```

Do not run expensive full project CI after every task or wave merely to imitate rigor. Native risk policy may require additional checks, but the default full self-hosted CI boundary is the phase candidate.

## Phase boundary protocol

The phase gate MUST bind Audit and Test to the final corrected phase candidate, while SEO OS contributes its applicable phase gate independently:

```text
all phase implementation/reviews converge
-> reconstruct phase denominator + affected public-search denominator
-> mechanical audit/component/design/SEO adapters as applicable
-> independent rendered/runtime audit
-> map findings to canonical TODO remediation
-> remediation + finding-specific reproduction
-> re-run applicable SEO phase verification on corrected surfaces
-> manual self-hosted CI on final corrected phase candidate
-> phase gate independent acceptance
-> next phase becomes eligible
```

If audit/SEO remediation changes code/config/content after CI, prior affected evidence is stale for the changed candidate and the affected final gate must be rerun.

This ordering deliberately catches defects before the next phase while avoiding a full slow CI run after every task.

## Long-running autonomous loop

A valid closure-oriented autonomous loop is:

```text
validate execution + Agent integrity
-> rehydrate/verify State OS
-> inspect configured SEO applicability/contract when applicable
-> resolve next lifecycle action
-> resolve minimum Agent OS context
-> inspect current code/history/evidence
-> implement/correct/resume/review/audit as routed
-> run targeted verification appropriate to that action
-> capture evidence
-> update canonical task state truthfully
-> commit/push when project policy requires it
-> revalidate execution state
-> when wave boundary is dependency-ready, execute its canonical audit gate
-> when phase boundary is dependency-ready, execute applicable SEO/A2 audit/remediation then final manual self-hosted CI gate
-> repeat until closed or truthfully blocked
```

The loop MUST respect user pauses, safety/authorization boundaries, resource limits and external blockers. Conversation history is not a substitute for repository-reconstructable state.

## Audit and SEO finding integration

Audit/SEO reports do not own remediation order. If either authority finds executable work:

1. create/reconcile the canonical TODO/native task with immutable ID and dependency placement;
2. keep the affected boundary gate non-terminal when required;
3. execute through normal lifecycle/reviewer separation;
4. reproduce the original failure/contract violation before marking its finding closed;
5. continue boundary closure only when policy permits every remaining disposition.

P0/P1/material audit or SEO debt must not be hidden in markdown, archived away or carried into later phases merely because implementation tasks were accepted.

## Execution document anti-patterns

Do not:

- restate entire product specifications;
- maintain a second checklist outside canonical task authority;
- track fake percentages manually;
- put every tiny task in a separate file;
- encode current code assumptions without repository inspection;
- allow `IMPLEMENTED` to mean done;
- treat `VERIFIED` as the preferred new-state name instead of `ACCEPTED`;
- skip audit/candidate/correction lanes because new READY implementation exists;
- represent an audit gate only in prose or route it to the implementer;
- treat an SEO report/contract as executable task authority;
- silently treat an invalid special task action as ordinary implementation;
- repeatedly select non-actionable blockers and starve independent work;
- allow an agent to skip required tests because the task description is detailed;
- mark a phase closed before its required audit/SEO/final candidate gates pass;
- run full slow CI after every task when targeted verification + boundary CI is the declared policy;
- defer all deep audit or search-architecture reconciliation until the end of the project and allow quality/search debt to compound.
