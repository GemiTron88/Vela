# Launch OS Capability — current 3.x

**Status:** CANONICAL capability guidance.  
**Mandatory:** Yes when the project will be deployed/distributed.  
**Purpose:** Turn an accepted codebase into a verified production release safely and reversibly.

## Authority boundary

Launch OS owns release-candidate, environment, deployment, rollback and post-launch gate policy. Agent OS may route launch/reviewer/operations skills and context; it does not authorize irreversible side effects or own task state. Execution OS/canonical TODO owns mutable implementation tasks generated by failed launch gates. Actual production actions additionally require the project-defined environment/side-effect authority.

SEO OS owns search applicability, public page-family intent/value, indexability/canonical/structured-data/programmatic policy and S0–S5 SEO semantics. Launch OS does **not** replace SEO OS; it makes the applicable SEO release/production gates mandatory at the correct release boundary and binds them to the same candidate/environment.

## Launch is a gate system

Launch should answer:

- what exact artifact are we shipping;
- whether the production environment can run it;
- whether migrations/data changes are safe;
- whether every applicable candidate-bound SEO gate is current for that artifact;
- how we observe success/failure, including search-facing production regressions where relevant;
- how we roll back or recover;
- what post-launch checks prove the release is healthy.

It must not become a second feature or SEO-remediation backlog.

## Release candidate identity

Before launch, record:

- commit SHA/tag;
- build/artifact version;
- environment;
- required gate results;
- accepted risks;
- configured control-file hashes required by candidate policy, including `executionkit.seo.json` when SEO is configured/applicable.

Any material code/config/content/search-contract change after candidate verification creates a new/stale candidate boundary unless policy explicitly and safely permits the change.

## Gate families

Use as applicable:

### Code/build

- tests/CI green;
- production build reproducible;
- dependencies locked/approved;
- static/security scans pass.

### SEO release / production

When SEO is applicable:

- **S3 / release:** `node bin/validate-seo.mjs . --release` and `release-readiness` must validate the exact candidate and current SEO contract hash;
- representative indexable page-family samples and declared technical/semantic checks must be current;
- **S4 / production:** after authorized deployment, verify production robots/status/redirect/canonical/sitemap/rendered/structured-data behavior declared by the SEO contract;
- **S5 / operations:** observe declared ongoing search-health signals and map material regressions to canonical TODO/incident authority.

A repository PASS never guarantees search-engine indexing, ranking, rich results or traffic. Search-engine observations are external evidence, not release permission by themselves.

### Data

- migration plan;
- backup available;
- restore procedure understood/tested at required risk level;
- destructive changes reviewed;
- backfill duration/locking considered;
- data validation after migration.

### Configuration/secrets

- environment variables present;
- production secrets not committed;
- credentials scoped correctly;
- third-party callback URLs/webhooks configured;
- feature flags intentional.

### Infrastructure

- compute/runtime versions;
- queue workers/schedulers;
- cache/session stores;
- storage permissions;
- CDN;
- DNS/TLS;
- mail/SMS/push integrations;
- scaling/capacity where relevant.

For public-search products, domain/TLS/host migrations, routing and CDN behavior must be reconciled with SEO redirect/canonical/sitemap/robots contracts before release.

### Observability

- logs;
- error reporting;
- metrics;
- health endpoints;
- alerts/on-call path appropriate to project size;
- declared SEO/search-health monitoring ownership where applicable.

### Product distribution

- app signing;
- store metadata/review;
- package versioning;
- web deployment routing;
- update/rollback mechanism.

### Analytics/privacy

- analytics events required for launch;
- consent/privacy controls;
- telemetry not leaking secrets/PII.

### Rollback

- rollback trigger;
- code rollback mechanism;
- migration compatibility;
- data repair considerations;
- communication/incident path;
- search-facing rollback/roll-forward strategy for material robots/noindex/canonical/redirect/sitemap/hreflang regressions where applicable.

### Post-launch

- smoke tests;
- critical journey check;
- queue/job health;
- error-rate check;
- migration/data spot-check;
- external integration check;
- applicable SEO S4 production checks;
- monitoring window based on risk, including S5 search-health signals where declared.

## Lite

Compact release checklist, backup/rollback note, smoke test and artifact identity. SEO may be `NOT_APPLICABLE` only after an evidence-backed surface decision; if applicable, the candidate S3 gate remains required even at LITE depth.

## Standard

Dedicated launch gates, environment checklist, migration/config/observability/rollback, applicable SEO S3/S4/S5 boundaries and post-launch verification.

## Full

Release-candidate freeze, formal gate evidence, rollback rehearsals where justified, data migration controls, multi-surface distribution checks, capacity/security reviews, search-facing production-change controls and incident readiness.

## Failed launch

If a Launch or applicable SEO release/production gate fails and requires implementation, create/map a canonical TODO task. Do not fix arbitrary code directly from a launch/SEO checklist without execution traceability.

## Opted-in product quality gate

When `quality.contractPath` is configured, release-readiness includes current quality evidence and fails on absent, failed, not-run or hash-stale results. Without a quality contract it explicitly reports `NOT_CONFIGURED`; native product gates are still required. Source hashes cover declared inputs only. Live services, field performance and environment-dependent behavior need fresh RC/launch checks. The product's VERSION is independent of `execution.config.standardVersion`.

## Candidate artifact gate

Required producer reports must agree with configured commands, current candidate/environment, successful process facts and ordered fresh timestamps. Artifact bytes must still match the collected SHA-256. Required test adequacy consumes a verified collected artifact, including when no producer IDs were explicitly required. Missing/null/duplicate evidence and null discovery inventory/reconciliation objects fail closed. These local integrity checks do not authenticate a runner or refresh external services.

When SEO is applicable, candidate identity also binds the current SEO contract control hash. Changing that contract after candidate creation makes S3 stale until the candidate/evidence is rebuilt and revalidated.

## Production side-effect and search-facing boundary

Before any irreversible/external action, establish:

- exact target environment/account/region/project;
- exact release candidate/artifact;
- explicit authority to perform the action;
- rollback/recovery path;
- expected bounded effect;
- evidence to capture afterward.

For public-search systems, changes to domains, redirects, robots, noindex, canonical, hreflang, sitemap generation or large route/indexability sets are production side effects. They require the same explicit target/rollback/evidence discipline; they are not incidental SEO cleanup.

Ambiguous target identity or missing authority is `BLOCKED`, not permission to infer.

## Final launch decision

The release may proceed only when:

- every mandatory pre-launch gate is `PASS` or explicitly accepted under project policy;
- applicable SEO S3 is current for the exact candidate;
- no unresolved P0/P1 launch/search blocker remains unless an authorized exception exists;
- candidate identity is frozen/known;
- deployment authority and target are known;
- rollback/recovery is viable;
- required production actions are authorized;
- smoke/health and applicable SEO S4/S5 procedures are ready.

After launch, capture the deployed artifact/commit/environment and smoke/health evidence. For applicable SEO surfaces, capture S4 production verification and ongoing S5 observations according to the owning SEO contract. Update applicable TODO tasks to `RELEASED` only when their semantics require release-state tracking and the evidence supports it.

Launch readiness, SEO S3 and production S4/S5 are separate evidence boundaries. None authorizes claims that a third-party search engine will index, rank or show rich results for a page.

## Host-isolated deployment fabric

For deployable projects Launch OS now owns a project-specific host readiness boundary:

```bash
executionkit launch host-plan .
executionkit launch host-check .
```

The Kit never assumes a universal hosting account/path. Normal release activation is unprivileged after one-time host provisioning. Workspace and production remain separate; production receives exact allowlist artifacts into immutable releases and switches an atomic current pointer.

Distribution/core/template repositories may be releasable but explicitly non-deployable with `distributionRepository=true` and `deployment.enabled=false`.
