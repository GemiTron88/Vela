# ExecutionKit v5: No Mandatory VPS Staging

**Owner decision: 2026-10-14. Canonical v5 portable distribution release policy.**

The standalone ExecutionKit v5 source/binary release does **not** require VPS Staging, a second server, temporary VPS staging instances, replicated MariaDB, permanent staging daemons, new test vhosts or CWP root access changes. Do not provision or test these just to issue Kit v5. The 2026-10-14 VPS1 receipts remain immutable historical evidence of tests already completed, not a recurring release dependency.

This choice does **not** remove Launch OS deployment safeguards. Every authorized **real customer/site activation** still requires exact-source artifact, signed independent approval, isolated project access, site-specific read-only vhost/host checks, backup/restore readiness, smoke/health checks, retirement/retention safety and rollback. Production customer changes remain separately authorized. Do not convert client deployment evidence to standalone Kit release status.

The v5 mandatory release closure is exact-SHA CI/source/distribution checks, eleven systems, real v4.1-v5 install+upgrade+rollback, meaningful consumer validation, signed native mobile artifact built and inspected directly on the approved physical Windows workstation (`executionkit launch mobile . --mode doctor|build|inspect|handoff|import`), Android installation/upgrade/data integrity, and independent owner go/no-go. By final owner decision, Launch OS executes web releases on VPS and native Android builds directly in the foreground on the owner's physical Windows workstation without requiring a background Local Build Agent, remote job polling/leasing, or Shorebird cloud patching (`mobileUpdateStrategy: SIGNED_APK`, `buildAgentRequired: false`, `shorebirdRequired: false`). Optional project-enabled Shorebird provider receipt is required only when `mobileUpdateStrategy: SHOREBIRD_OPTIONAL` is explicitly selected for a provider path. No native builds on VPS.

**Disk economy is part of Launch OS acceptance:** release payloads exclude documentation, tests, test fixtures, source control, caches, credentials and build-time node_modules except a narrowly justified executable runtime such as Next standalone. Composer vendor is production-only and verified locked/no-dev. Retention automatically prunes only known healthy inactive releases and source artifact copies when safe, preserves current/rollback, shared uploads/storage/.env, backups, in-use workers and unverified legacy directories. Explicit storage audit is read-only; owner handles unknown historical deployments separately. Do not disable fail-closed checks or delete directories with broad shell glob patterns.

No new OS/daemon, no mandatory background Build Agent, no mandatory Shorebird dependency, no recurring staging, no repeated full suite per task. Preserve exact failure evidence and concise default output. No stable tag or publication without explicit owner's later approval.

## Read-only disk inspection

`executionkit launch storage . --json` inspects the configured release tree and producer artifacts only on explicit request (bounded to 25,000 filesystem entries). It reports counted file bytes and which versions are current/rollback/inactive without deleting anything or following symlinks. A truncated scan is `REVIEW`, not proof of complete disk usage. Automatic cleanup runs only after healthy authorized deployment and can be `DEFERRED` for busy/uninspectable workers, grace periods or unknown legacy directories. The v5 default retains **one** rollback; an explicitly configured `keepRollbacks: 0` requires a separate verified worker-retirement barrier. Composer `vendor` is required production runtime, while `.next/standalone/node_modules` may be necessary for production Next.js standalone; ordinary `node_modules` are excluded. SQL backups and owner folders are never automatically purged.

**Avoid duplicate artifact copies:** v5 defaults retain the live current release and one live rollback (`keepRollbacks: 1`) while retaining only the current producer build cache (`artifactKeepRollbacks: 0`). A project may override these independently; unverified old directories or user data are never automatically purged. Producer artifact cache pruning does not remove the live rollback tree.

**Immutable producer cache reuse:** repeated builds for the same clean source reuse verified existing artifact bytes, avoiding duplicate copying. Tampered payloads and unknown owner files block cache reuse rather than being silently erased. The active production release remains immutable.

**Already-installed consumer projects:** new defaults apply to new v5 installations and only to projects without explicit retention overrides. Never silently rewrite a client's release policy. On a project retaining many previous releases, run the read-only `launch storage` audit, inspect worker ownership, unknown legacy data and prior cleanup reasons; then authorize only a project-scoped safe policy adjustment and normal healthy next deployment. The Kit source update itself does not remove existing customer server files. After any exact-source code change, old GitHub Source RC acceptance is stale until rerun.

**Installer vs production:** Installer-managed `.agents` and `.executionkit/runtime/kit` are intentionally maintained in development/agent worktrees. Only allowlisted Launch payload is deployable; copying the entire working repository into a site, public_html, or the live release root bypasses this contract and is not supported. `executionkit launch storage .` flags such control-plane leakage in a configured active release without touching it. `node .executionkit/runtime/kit/bin/inspect-workspace-storage.mjs . --max-entries=60000` runs **only from the project root** containing a valid `execution.config.json`, inventories files inside that project, and rejects parent/home/other-project paths. It does not traverse symlinks or cross-device mounts. No system-wide or Antigravity-home audit is provided. Never delete managed `.agents` or installed runtime automatically.

**Interrupted producer builds:** new source artifacts are first copied to an invocation-owned temporary directory, then published by rename. Normal copy/hash failures remove only that newly created path; verified producer artifacts, live rollback versions and project files are never touched. Process-killed leftovers still require bounded owner-proven cleanup rather than wildcard deletion.
