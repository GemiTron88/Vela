# Second audit: product completeness and evidence integrity

Reviewed 2026-09-09 against live main
`85a63672d3adb402046a816fcc7d770445ffd733` (v2.1.0), tree
`f0a5abcb9988d375f6a9377c49bcca8217b5adb3`. The local baseline tree matched
GitHub exactly before changes. This review concerns the central distribution;
no adopting application's implementation or installed IDE was audited here.

## Verdict

The six-capability architecture is a useful delivery foundation. The system is
**not completely integrated, exhaustive or sufficient by itself to guarantee a
premium product**. v2.1 has deterministic execution/routing and declared quality
evidence validation. It does not have automatic full-product discovery, a shipped
web/Flutter component library, raw-report acceptance adapters or a proven live
Antigravity execution environment. The existing 77 passing tests did not expose
the defects reproduced below; test count was not a completeness measure.

The review compared normative contracts, runtime validators, project bootstrap
and release behavior, Agent/stack skills and product-quality documentation with
the requested workflow. Five additional negative tests were run against the
unchanged v2.1.0 implementation before fixes; all five failed their assertions.
That result is retained in `v2.1.1-before.log`.

## Confirmed defects corrected in v2.1.1

| Finding | Reproduction and impact | Correction |
| --- | --- | --- |
| High: non-object evidence could bypass release validation | A valid declared contract with an evidence file containing JSON `null` returned no quality errors. The `if (report)` branch skipped the entire report check. | Require an object after a successful JSON parse; reject falsy and other primitive/array values. Full release-command regression covers terminal TODO, clean synchronized git and a null report. |
| Medium: malformed contracts could crash instead of yielding diagnostics | A null contract threw while reading schemaVersion; a numeric requiredDimensions could throw through includes. | Validate object/array shapes before accessing them; return structured errors. |
| Medium: published schema and runtime behavior differed | Numeric indexable and unsupported fields could pass even though the JSON schemas forbid them. Some invalid dates were normalized by Date.parse. | Enforce boolean flags, closed properties, result/hash types and explicit valid date/time/timezone input. Explicit malformed quality config is not treated as opt-out. |
| Medium: dangling symlinks escaped the path guard | existsSync returned false for a symlink whose target did not exist, so projectFile accepted it as a writable managed path. | Inspect the directory entry using lstat regardless of target existence. A regression checks refusal before configuration changes or external target creation. |
| Medium: doctor could report ok for invalid execution state | A canonical task with Status MADE_UP produced ok=true because diagnosis loaded tasks without running execution validation. | Include execution integrity; report the validator failure and suppress next-task suggestions until repaired. |

These fixes enforce existing contracts. They do not create another OS, change
canonical task state or opt existing products into a new quality profile. The
quality schema stays at 1.0.0. Valid existing reports retain their format; invalid
reports that previously slipped through must be corrected and regenerated.

## What exists versus what still needs implementation

The following is an assessment and a set of design proposals, not an executable
backlog or a claim that these additions were built in this patch. Any selected
implementation must first map to the target project's canonical TODO. Preserve
stronger project-native implementations when they already solve the problem.

| Area | Verified current capability | Remaining implementation that matters |
| --- | --- | --- |
| Scope and coverage | Manual subjects, dimensions and TODO links are checked. | Discover actual routes, database-backed slugs, navigation, widgets/custom elements and content taxonomy; reconcile discovered items with declared requirements and explicit exclusions. |
| Premium design and components | Skills and prose require tokens, brand direction, component families and states. | A real product-specific component catalog, typed API/variant/state contracts, rendered examples and web/Flutter parity evidence. No prebuilt implementations exist in this distribution. |
| Visual and accessibility acceptance | Visual dimensions require a distinct reviewer string and hashed artifacts. | Browser/axe and Flutter golden/semantics adapters, controlled baselines, independent art-direction review and real device/state matrices. Reviewer identity is not authenticated. |
| SEO and performance | Guidance covers search architecture and suggested Lighthouse/field budgets. | Execute and interpret raw reports against inventoried route families, measure production builds, verify crawl/index/structured-data behavior and observe field data. The validator does not parse scores or guarantee rankings. |
| Test adequacy | Kit tests and declared per-requirement evidence checks. | Native reporters that reject zero applicable tests, required skips, flakes and mock-only E2E; real business/security/integration assertions. An exitCode of zero alone cannot prove those conditions. |
| Release identity and freshness | Hashes for explicitly listed sources/artifacts; local git closure checks. | Candidate/build identity, dependency/scope-change invalidation, environment binding, freshness limits and trusted evidence producers. Unchanged listed files do not prove a current runtime observation. |
| Rich content | Domain/localization/provenance guidance and a content dimension. | Project content schemas, production imports/assets, missing/thin/duplicate-content checks, rights/provenance review and actual refresh monitoring. No production content catalog is included. |
| Antigravity and automation | Native discovery files, tag/lifecycle routing, initial read-only context injection and diagnosis. | Installed-version smoke evidence, actual Boost/Dart MCP calls, evidence collection, bounded recovery and resource limits. Current routing does not enforce process budgets or run a continuous autonomous acceptance loop. |
| Domain and operational reliability | Laravel/Flutter and Test/Launch guidance mentions relevant risks. | Project-specific executable tenant/permission, money, idempotency, offline reconciliation, migration/restore and post-launch health gates. These cannot be inferred merely from a premium UI profile. |

## Recommended order for the requested workflow

First establish the **coverage denominator and evidence pipeline**. Otherwise a
beautiful tested screen can coexist with unlisted broken screens, and empty test
runs can be mistaken for completed verification. Discovery must compare actual
implementation with approved scope: scanning code alone cannot discover a planned
feature that was never implemented. Dynamic routes need representative valid,
empty, missing, denied and locale-specific data rather than URL strings alone.

Then build a **premium reference slice** within one real product: a dense data
surface, a multi-state form/overlay and a critical recovery journey, with Flutter
parity where required. Use approved native brand tokens and real domain behavior.
Include Arabic-first typography, RTL/LTR, long and sparse content, themes, keyboard,
screen readers, text scaling, narrow/wide layouts and applicable offline states.
Premium means deliberate art direction, useful information and complete behavior;
it does not mean gratuitous motion or recreating the same generic dashboard.

Turn the verified slice into a **maintained component system**, not a folder of
unrelated snippets. Each adopted family needs its public API, variants, states,
accessibility behavior, token dependencies, supported platforms and examples/tests.
Advanced families may include grids with bulk operations, rich editors, uploads,
media, calendars, charts, maps and domain-specific controls when needed. Share
semantic tokens and behavior across web/Flutter; preserve platform-native details.
Maintain explicit supported coverage, never promise a library that covers every
possible future component.

Attach **SEO/performance/content checks** to the discovered public inventory and
critical authenticated journeys. Test useful content and actual HTML/navigation,
not metadata presence alone. Lighthouse assertions must use a failing level for
required budgets and an explicit aggregation method; raw results and the measured
build/environment must be retained. Field data may legitimately be unavailable.
Flutter needs profile/release device measurements independently from browser runs.

Finally strengthen **candidate acceptance and bounded automation**. Derive affected
checks from implementation/shared dependencies, collect raw outputs with candidate
identity, and preserve interrupted work across sessions. Runtime orchestration
needs explicit limits, cancellation, task ownership and recoverable checkpoints;
a hook or role file alone does not implement those controls. Keep expensive suites
deliberate and the established self-hosted manual CI policy. Required failures
remain visible; do not convert a repeated failure into success by weakening gates.

For active products, preserve data, IDs, history and stronger native contracts.
Incremental replacement needs coexistence/feature flags, authorization and parity
tests, reconciliation, UAT and the required production observation period before
the prior interface is retired. Financial authority and state transitions stay on
the server; client parity must not weaken those invariants.

## OS decision

No additional OS is required by these findings. Experience/components are governed
through Agent + Test + Audit; content and SEO through Content + Test + Launch;
evidence and runtime reliability through Test + Audit + Launch. Execution remains
the sole task-state authority. A future OS would need a distinct decision owner
and lifecycle that cannot be expressed clearly within these six. More named OSs
would not implement missing adapters, component code or runtime tests.

## Verification and limits

Final full distribution output is retained in `v2.1.1-validation.log`; it includes
the kit tests, all three example profiles, CI-policy and distribution checks.
Result: **82 tests passed, zero failed, zero skipped; all example, CI-policy and
distribution checks passed.** The final diff also passed whitespace validation.
The validation environment is Linux x64 / Node v24.19.0. The negative regressions
cover rejection and recovery, including a complete release check. The symlink
test can explicitly skip on Windows without symlink privileges; no Windows/macOS
execution is claimed by this Linux run.

No real application browser/device suite, production content audit, visual design
acceptance, Lighthouse run, live MCP query, installed Antigravity session, physical
runner registration or GitHub Actions dispatch was performed. Those remain
product/environment acceptance steps. No percentage of overall completeness is
reported because no complete product denominator has been established here.
